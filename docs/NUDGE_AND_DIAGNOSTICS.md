## 一、四类提示场景

| 场景 | 触发时机 | 模块 | 文案 |
|------|---------|------|------|
| 1. 设备支持 NPU，未启用 | 首次启动 + 加载模型后 | `feature/chat` (NudgeDecider v2) | "当前 小型 模型仅 5.2 tok/s..." |
| 2. 模型量化可能不支持 NPU | 加载模型时 | `core/diagnostics` | "该量化的模型可能无法成功启用 NPU 加速（高通 Hexagon）。" |

| 4. NPU 可用性引导（首次） | App 首次启动 onboarding | `core/diagnostics` + `feature/onboarding` | "您的设备支持 NPU 加速，启用 NPU 后端之后速度可能会更快" |

### 1.1 提示 1：模型性能引导（已实现）

详见 [PERFORMANCE_NUDGE.md](./PERFORMANCE_NUDGE.md)。核心：双因子判定（模型参数量 + 实际 tps）。

### 1.2 提示 2 / 3：量化兼容性（新实现）

模型加载时调用 [NpuCompatibilityDiagnostics]，返回 4 档判定：

| 判定 | UI 表现 |
|------|---------|
| `FullSupport` | 静默，无提示 |
| `PartialSupport` | 模型信息页角落小标签："部分加速" |
| `QuantUnsupported` | 模型加载完弹卡片："该量化的模型可能无法成功启用 NPU 加速" |
| `FormatUnsupported` | 模型加载完弹警告："该量化格式不受支持，速度会显著变慢" |

判定矩阵（详见 `core/diagnostics/NpuCompatibilityDiagnostics.kt`）：

| 量化 | Hexagon V73~V81 | 华为 HiAI | 联发科 NNAPI | 通用 NNAPI |
|------|----------------|----------|-------------|-----------|
| INT8 | ✅ 原生 | ✅ 原生 | ✅ 原生 | ✅ 原生 |
| INT4 | ✅ 原生 | ⚠️ 视设备 | ⚠️ 视设备 | ⚠️ NNAPI 1.x+ |
| F16 | ❌ 不支持 | ⚠️ 兜底 | ⚠️ 兜底 | ⚠️ 视厂商 |
| Q4_0/Q4_1 | ⚠️ 部分加速 | ❌ 不支持 | ❌ 不支持 | ❌ 不支持 |
| Q4_K/Q5_K | ❌ 不支持 | ❌ 不支持 | ❌ 不支持 | ❌ 不支持 |
| Q8_0 | ⚠️ 需转 INT8 | ❌ 不支持 | ❌ 不支持 | ❌ 不支持 |
| F32/BF16 | ❌ 格式不支持 | ❌ 格式不支持 | ❌ 不支持 | ❌ 不支持 |

## 二、基准测试设计（基础 + 高级）

### 2.1 双档模式对比

| 模式 | BASIC | ADVANCED |
|------|-------|----------|
| 目标用户 | 普通用户对比后端 | 发烧友调优 |
| 时长 | 30 秒 | 120 秒 |
| 采样间隔 | 1 秒 | 0.5 秒 |
| 显示指标 | 3 项平均 | 6 条曲线 + 3 项平均 |

### 2.2 BASIC 模式输出

```
基础基准测试 · 后端：llama.cpp · 模型：Qwen2-1.5B-Q4_K_M
─────────────────────────────────────────
输出速度（平均）：    25.3 tok/s
预填充速度（平均）：  142 tok/s
内存占用（平均）：    1.2 GB
─────────────────────────────────────────
[重新测试] [导出报告]
```

### 2.3 ADVANCED 模式输出

包含 6 条曲线 + 基础 3 项汇总：

```
高级基准测试 · 后端：Hexagon V75 · 模型：Qwen2-1.5B-Q8_0
─────────────────────────────────────────

📊 基础指标（平均）：
   输出：    142 tok/s
   预填充：  680 tok/s
   内存：    1.4 GB

📈 详细曲线：
   ① 内存占用率（0-100%）
   ② 预填充速度波动（tok/s）
   ③ 输出速度波动（tok/s）
   ④ 温度波动（CPU/GPU/NPU ℃）
   ⑤ NPU 占用率（含空闲基线对比）
   ⑥ CPU 占用率（仅本进程）

⏱ 耗时 120s，共 240 个采样点
[导出 CSV] [导出报告]
```

### 2.4 NPU 占用率"空闲基线"实现

测试启动前先采样 5 秒空闲 NPU 占用率作为基线（如 8%），
推理中实时采样对比（如 65%），
曲线上画两条线：基线（虚线）+ 实时（实线）。

**部分厂商 API 不公开占用率**（用户已允许"展示不了可以不写"）：
- 华为 HiAI：✅ 有 `getNpuUtilization()` API
- 高通 QNN：⚠️ 仅部分版本支持
- 通用 NNAPI：❌ 无标准 API
- 实现：API 不可用时返回 null，UI 隐藏该曲线，显示"该硬件不支持 NPU 占用率采样"占位

### 2.5 CPU 占用率（仅软件内）

只统计 AIBox 进程的 CPU 时间，不读系统级（避免读取其他应用 CPU 时间涉及隐私）：
- 读 `/proc/self/stat` 的 utime + stime 字段
- 计算两次采样间隔的差值 / 间隔时间 / CPU 核数
- 返回 0..1 的占用率

## 三、自动调优（TokForge 风格）

### 3.1 三档粒度

| 粒度 | 测试组合数 | 测试维度 | 耗时估算 |
|------|----------|---------|---------|
| **低** | 3 | KV cache / CPU 线程数 / 后端切换 | ~3 分钟 |
| **中** | 6 | +批处理 / 上下文长度 / GPU 层数 | ~6 分钟 |
| **高** | 12+ | +量化对比 / MTP 开关 / 内存策略 | ~12 分钟 |

### 3.2 调优维度（9 项）

| # | 维度 | 关键参数 | 含义 |
|---|------|---------|------|
| 1 | KV cache | 512 / 1024 / 2048 | 长上下文性能 vs 内存 |
| 2 | 批处理大小 | 1 / 8 / 32 | 吞吐量 vs 延迟 |
| 3 | CPU 线程 | 2 / 4 / 8 | CPU 后端速度 |
| 4 | 后端切换 | llama.cpp / NNAPI / Hexagon | 后端最优 |
| 5 | 上下文长度 | 2048 / 4096 / 8192 | 长对话能力 vs 内存 |
| 6 | GPU 层数 | 0 / 10 / 99 | llama.cpp 的 gpu-layers |
| 7 | 量化对比 | Q4_K_M / Q5_K_M / Q8_0 / F16 | 多档压缩对比 |
| 8 | MTP 开关 | on / off | Multi-Token Prediction |
| 9 | 内存策略 | mmap / mlock / full-load | 内存分配策略 |

### 3.3 流程

```
用户点"开始自动调优"
   ↓
选择粒度（低/中/高）+ 优化目标（tps优先/内存优先/平衡）
   ↓
[AutoTuner] 按 [TuneCombinationPlanner] 生成测试组合列表
   ↓
对每个组合：
   1. 加载模型（如需切换量化则切换模型文件）
   2. 跑 [BenchmarkRunner] 测 30s
   3. 记录 tps / prefillTps / 内存 / 延迟
   4. 计算综合得分
   5. 流式推 [TuneProgress.Running] 到 UI
   ↓
所有组合跑完：
   [TuneProgress.Done] 携带最优推荐 + 全部结果
   UI 显示对比表 + 推荐"启用此配置"按钮
```

### 3.4 优化目标评分公式

| 目标 | 公式 |
|------|------|
| TPS 优先 | `score = tps` |
| 内存优先 | `score = 1 / memoryMb * 1000` |
| 平衡 | `score = tps * 0.7 + (1000 / memoryMb) * 0.3` |

### 4.2 项目野心大的根本原因

10+ 个核心功能模块 + 5 个核心契约接口 + 17+ 个 Gradle 模块（骨架）+ 7 个推理后端 + NPU 加速 + 插件生态 + 双轨日志 + 性能诊断 + 自动调优 + 断点续传 + 完全离线 + 完全开源。

> 这不是"能跑就行"的项目，是"必须从一开始就不能让屎山存在"的项目。
> 因为一旦功能模块多到 10+，任何一处架构松动都会乘 N 放大。

## 六、模块新增检查表（避免屎山）

新增任何"性能诊断类"功能前，必须问：

- [ ] 触发逻辑是否独立成纯 Kotlin 类？（便于单测）
- [ ] 阈值是否集中定义？（禁止散落 magic number）
- [ ] 文案是否在数据类里生成？（避免 UI 拼字符串）
- [ ] 用户偏好是否可持久化关闭？（DataStore）
- [ ] 是否有冷却期？（避免连发提示）
- [ ] 失败兜底路径是否定义？（API 不支持时 UI 显示什么）

新增任何"采样源"前，必须问：

- [ ] 接口是否做了 null 兜底？（API 不可用返回 null）
- [ ] UI 是否检查了 null 并显示占位文案？
- [ ] 单元测试是否覆盖了"API 不可用"分支？
- [ ] 隐私边界是否清晰？（如只读自己进程的 CPU 时间）
